# Final adversarial review — confirmed findings

Six reviewers (one per dimension) reported defects with repros; an independent skeptic re-ran each repro.
Only findings the skeptic reproduced ('confirmed') are listed. Fix status is tracked in docs/dev/HANDOFF.md.


## geometry

### [HIGH] GEO-1: A glove-trained hand_mano policy gets robot taxel poses in the URDF root frame at deployment, not the MANO hand frame it was trained in

- files: robot_skin/control/online.py, robot_skin/stages/deploy.py, robot_skin/control/runner.py, docs/ARCHITECTURE.md
- problem: The VTLA policy is trained on glove D2 episodes (vtla.yaml: datasets [task], action kind hand_mano). Those episodes store taxel_pos and taxel_nrm in the MANO wrist frame: fingers point -x, the palm faces -y (build.py _taxel_poses, glove_pose_fn). At deployment on a robot, build_processor -> OnlineTactileProcessor -> make_pose_fn -> robot_pose_fn returns taxel poses in the URDF root frame. For the synthetic hand that frame has fingers along +z and pads facing +x. PolicyRunner._policy_tick passes frame.pos and frame.nrm straight into make_observation, and TaxelTokenizer encodes absolute fourier(pos) plus the normal. Nothing re-expresses the robot poses in the MANO frame (for example R_hr^T p / scale). The rotation needed is SYNTHETIC_HAND_HUMAN_TO_ROBOT, but only the retargeter uses it. As a result every glove-to-robot deployment feeds the tactile encoder positions and normals rotated by about 90 degrees and shifted by centimetres from the training distribution. The docs claim the opposite: ARCHITECTURE.md says '손 프레임이라 글러브·로봇이 인코더를 공유' (both are in a hand frame, so glove and robot share the encoder), and section 4 says the two hands can share the tactile encoder.
- suggested fix: When the bundle was trained on MANO-frame (glove) taxel poses and runs on a URDF skin, map the robot poses into the MANO hand frame before make_observation: pos' = R_hr^T (p - p_base) / scale and nrm' = R_hr^T n, using the retargeter's human_to_robot, scale and base_link. Store the training taxel_frame in the bundle meta and have deploy check it. Otherwise document that glove-trained tactile encoders do not transfer as they are.

### [MEDIUM] GEO-2: map_taxel_values mixes values across finger groups when k exceeds the number of same-group sources (reduce='max', and NaN in 'weighted')

- files: robot_skin/transfer/align.py
- problem: align_layouts(by_group=True) sets the distance of cross-group sources to inf, but it still returns them in index[:, :k] when a destination's group has fewer than k sources. The weights of those sources are 0, but map_taxel_values ignores weights for reduce='max' (g.max(-1) over all k indices). A contact flag or level on one finger is therefore copied to every other finger. This breaks the documented rule 'never across finger groups', and the README recommends 'max' for levels and flags. reduce='weighted' computes sum(g * w), so a NaN on any cross-group source gives 0*NaN = NaN at the destination. max_dist is also checked only against the nearest match, so matches 2..k beyond max_dist still contribute. With the shipped templates each fingertip group has one taxel per hand, so any k >= 2 triggers the leak.
- suggested fix: In map_taxel_values, mask entries whose weight is 0 or whose distance is not finite: for 'max', replace those gathered values with the dtype minimum (or False) before the max; for 'weighted', use np.where(w > 0, g, 0) before the sum. Alternatively, have align_layouts truncate each row to its finite matches (store a per-row count or pad with -1), and apply max_dist to every match, not only the first.

### [LOW] GEO-3: Skeleton-space alignment of the shipped glove and robot templates maps a palm pad across the hand midline (radial-distal <- ulnar-distal)

- files: robot_skin/transfer/skeleton.py, robot_skin/transfer/align.py
- problem: The palm lateral coordinate v comes from the single nearest palm capsule (PALM_LATERAL ∈ {-1/3, 0, 1/3, 2/3, 1}), so it is quantized. The glove's radial-distal pad palm_11 (x=+12 mm radial in the palm frame) is closest to the palm_index capsule (v=0). The robot's radial-distal pad palm_11 (y=+15 mm radial) is closest to palm_link>middle (v=1/3). The glove candidates for robot palm_11 are palm_11 (v=0) and palm_10 (v=2/3, the ULNAR-distal pad), both |dv|=1/3 away, so the u term decides and picks the ulnar pad. In the reverse direction, glove palm_11 takes robot palm_01 (radial-proximal) instead of robot palm_11. The robot template says it has the 'same topology as glove_template', but the default cross-embodiment mapping sends glove palm_10 to two robot pads, including one on the opposite side of the hand, and never uses glove palm_11. The transfer tests check only the proximal palm pads (index[5] and index[6]).
- suggested fix: Use a continuous lateral coordinate for palm taxels, for example by interpolating PALM_LATERAL between the two nearest palm rays by distance or angle around the wrist, or by projecting onto the index-to-pinky knuckle line. Add a test that all four template palm pads map one-to-one with lateral sides preserved.

### [LOW] GEO-4: vec_frame='world' IMU features are inconsistent with calibration: world-frame gyro/acc are rotated by per-site mounting offsets and never by G^-1

- files: robot_skin/pose/imu_model.py, robot_skin/pose/glove_imu2mano.py, robot_skin/datasets/build.py
- problem: imu_features offers vec_frame='world' 'for devices that output world-frame vectors', and stages/imu_pose exposes it through features.vec_frame. Calibration does not handle that case. datasets.build._process_imu and GloveImu2ManoPoseProvider always call apply_imu_offsets_to_vectors (R_off^T v), which is only correct for SENSOR-frame vectors, while apply_imu_offsets moves the quaternions into model world (G^-1 ⊗ q ⊗ q_off). For world-frame vectors the correct map is G^-1 v; the per-site mount rotation is wrong for them. imu_features(vec_frame='world') then computes R_wrist_model^T R_off_site^T v_imuworld, which mixes frames. The features become wrong by the size of gravity and depend on the session's arbitrary IMU heading G. This breaks the documented invariance to a common world rotation.
- suggested fix: Make the vector calibration frame-aware: for world-frame vectors apply G^-1 (quat_apply(conj(G), v)) and skip the mount offset. Record the vector frame in preprocessing meta and pass it through build/provider. Or remove vec_frame='world', since DATA_FORMAT.md already requires sensor-frame gyro/acc.

### [LOW] GEO-5: build_retargeter bypasses the scale > 0 check: scale 0 or negative in deploy.yaml is accepted and a flat hand is commanded as a fist

- files: robot_skin/stages/deploy.py, robot_skin/action/retarget.py
- problem: FingertipRetargeter.__init__ rejects non-finite or non-positive scale. stages.deploy.build_retargeter builds the retargeter with the default scale=1 and then assigns rt.scale = float(cfg['scale']) with no validation. A config typo such as scale: 0, -1 or .nan passes silently into the robot controller. With scale 0 every human vector target collapses to 0, so a flat human hand drives the robot to curl its fingers to the limits. With scale -1 the fingers are mirrored. The retarget config is otherwise strict about typos (from_config and load_stage_config raise on unknown keys).
- suggested fix: Pass the resolved scale to the FingertipRetargeter constructor, estimating it first with a temporary instance or by computing the ratio directly. Or validate it before assignment: `if not (math.isfinite(s) and s > 0): raise ValueError(...)`. Making scale a validated property on FingertipRetargeter also covers RobotToManoEstimator, which reads fwd.scale.


## data

### [HIGH] DP-1: hand_pose.npz added the documented way is silently ignored by preprocessing, so glove sessions get no q, no self-touch labels and no hand-pose labels

- files: robot_skin/datasets/build.py, docs/DATA_ACQUISITION.md, docs/DATA_FORMAT.md, robot_skin/pose/vision_hand.py, robot_skin/acquisition/recorder.py
- problem: On real hardware the recorder's session.json has no `hand_pose` stream, because labels come from HaMeR/WiLoR run offline later. DATA_ACQUISITION.md §9 says: "hand_pose.npz 는 기록 후 pose.vision_hand.save_hand_labels 로 같은 디렉터리에 추가한다" (add it to the same directory with save_hand_labels). DATA_FORMAT §1.5 gives the same procedure. However, build.py:654 only reads hand labels when `"hand_pose" in man.streams`. Neither save_hand_labels nor any other tool registers the stream: no helper exists, and only the HaMeREstimator docstring mentions 'register the stream in the manifest'. The result: every real glove episode is built with no q/qd, no hand_pose_valid, no self_touch (so zero contact_label==1) and constant rest-hand taxel poses. The note it records even says "no hand_pose.npz" although the file exists. Downstream, the baseline stage skips every glove episode ('missing q') and the imu_pose stage has no labels. The source fingerprint only hashes manifest-listed files, so adding the npz later is not reported as stale either. object_pose.npz, also an offline product, has the same gate (build.py:678). Fake/synthetic sessions register hand_pose, which is why the tests pass.
- suggested fix: In build, fall back to `<session>/hand_pose.npz` (and object_pose.npz) when the file exists but is not in manifest.streams, and record a note. Alternatively, make save_hand_labels (given a session dir) register a StreamInfo in session.json, and include these canonical files in _source_fingerprint. Update DATA_ACQUISITION §9 either way.

### [MEDIUM] DP-2: Correcting event boundaries in events.jsonl (the documented fix) never reaches contact labels or the baseline window: stale manifest.segments win

- files: robot_skin/datasets/build.py, robot_skin/acquisition/session.py, robot_skin/acquisition/recorder.py, docs/DATA_ACQUISITION.md
- problem: The recorder turns phase events into manifest.segments once, at stop() (_finalize). DATA_ACQUISITION.md §9 says boundary fixes are made by editing/adding lines in events.jsonl and then re-running `python -m robot_skin.acquisition.session <dir>`. postprocess_session only re-runs sync, IMU calibration and QC; it never regenerates manifest.segments. build.py then uses `segments = list(man.segments) or segments_from_events(...)` (line 690, and line 770 for the baseline), so the old segments always win. Meanwhile phase_id/meta.phases, sync windows and the calibration phase are rebuilt from the edited events. The processed episode ends up inconsistent: frames that the operator removed from a no_contact block (for example because the subject touched the palm) keep contact_label==0. They are therefore used as no-contact regression targets by BaselineWindowDataset, and as calibration and negative data by the contact stage.
- suggested fix: Make events.jsonl the single source of truth. Either build derives segments from events (keeping only explicitly added, non-phase segments such as 'task' from the manifest), or postprocess_session regenerates manifest.segments from events (keeping Recorder.add_segment extras). At minimum, warn in build when manifest segments disagree with segments_from_events(events).

### [MEDIUM] DP-3: Detector and pretraining learn from the baseline's in-sample residuals, so no-contact z on the training data is far tighter than at test time

- files: robot_skin/stages/contact.py, robot_skin/stages/baseline.py, robot_skin/stages/pretrain.py
- problem: The contact stage is careful to fit the ResidualCalibrator on the val split, 'the baseline did not train on them'. However, it then trains the ContactDetector, its qd NormStats and the bootstrap labels on split['train'], using derived residual_z of exactly the episodes the baseline trained on. Those are in-sample baseline predictions. The pretrain stage likewise trains on D1-train residual_z and contact_level. In-sample residuals are much smaller than out-of-sample ones, so the detector sees a no-contact z distribution at training time that it never sees on val, test or deployment. This is classic stacking leakage and pushes it toward false contacts on new data. It is not documented anywhere; only imu_pose notes the analogous problem.
- suggested fix: Train the detector (and fit its stats and bootstrap labels) on residuals the baseline did not see. Options: cross-fitting / out-of-fold baseline predictions for the D1 training episodes (k-fold baseline, write OOF residuals), or train the detector on a held-out D1 split disjoint from the baseline's training set. At minimum, document the bias and report the train-vs-val residual gap in metrics.

### [MEDIUM] DP-5: Robot joint_state names that don't match the URDF produce q ≡ 0 and qd ≡ 0, with nothing recorded in the episode

- files: robot_skin/datasets/build.py, robot_skin/pose/urdf.py
- problem: _process_joints calls URDFModel.reorder_q(q, names), which fills every URDF joint absent from `names` with 0 and only emits a Python warnings.warn. If none (or most) of the driver's names match, q and qd become all zeros and taxel poses become static. This happens with a common ROS namespace prefix such as 'rh_thumb_mcp' vs 'thumb_mcp', or with the fake robot's 'thumb_j1' names plus an explicit robot.urdf. Yet meta.preprocessing reports q_source='joint_state', joint_names in URDF order, and notes=[]. The episode looks healthy: the baseline trains on constant joints and the contact stage then sees raw ΔS as residual. DATA_FORMAT documents '빠진 관절은 0 + 경고' (missing joints → 0 + warning) for the partial case, but a total or near-total mismatch is silent data loss.
- suggested fix: In _process_joints, compute the overlap between driver names and model.joint_names. Raise (or refuse to build) when the overlap is empty or below a threshold. Otherwise append the list of zero-filled joints to `notes` and meta.preprocessing (e.g. `zero_filled_joints`) so stages can skip or flag such episodes.

### [LOW] DP-6: Timestamp gaps in pressure/IMU/joint streams are linearly bridged and treated as measured data

- files: robot_skin/datasets/build.py
- problem: build flags non-finite pressure samples as saturated. Missing samples (USB/serial stalls, i.e. gaps in `t`) are simply np.interp'ed across onto the 200 Hz master grid. No validity mask is stored for pressure, IMU or joint_state, so the fabricated frames look like measurements. Consequences:
- Inside no_contact segments, interpolated ΔS ramps get contact_label 0 and become BaselineWindowDataset regression targets.
- A press that happens inside a gap disappears.
- IMU gaps give fabricated IMU features next to valid vision labels in ImuPoseWindowDataset.
The acquisition QC passes gaps up to 0.5 s and 2 % drops, and preprocessing does not consult QC by default (DP-7), so such gaps reach training.
- suggested fix: Mark master frames whose bracketing native samples are more than k·(1/rate) apart as invalid: flag them saturated/untrusted for pressure, and store imu_valid / q_valid masks for IMU and joints that q_valid_mask/qd_valid_mask and the datasets honour. Record gap counts in meta.preprocessing.notes.

### [LOW] DP-7: Preprocessing builds sessions that failed QC by default, contrary to the acquisition procedure

- files: robot_skin/datasets/build.py, robot_skin/configs/stages/preprocess.yaml, docs/DATA_ACQUISITION.md
- problem: DATA_ACQUISITION §10 says FAIL sessions should be left in place (not deleted) and re-recorded into a new directory, and that preprocessing targets are filtered by qc.json `passed`. But DEFAULTS['qc']['skip_failed'] is False, and `python -m robot_skin preprocess` / build_all over the raw root builds every session, including qc.json passed:false. Following the documented procedure therefore puts both the failed take and its re-take into the processed dataset and all splits. Examples of failed takes: dropped samples, saturation during no-contact blocks, baseline drift.
- suggested fix: Default qc.skip_failed to true (report skipped sessions as qc_failed, as build_all already supports). Alternatively, change DATA_ACQUISITION §10 to say explicitly that preprocessing must be run with --set qc.skip_failed=true.

### [LOW] DP-8: With clock.span: pressure, edge-held IMU and joint streams are treated as valid measurements

- files: robot_skin/datasets/build.py, robot_skin/datasets/stats.py
- problem: With the documented option clock.span: pressure, the master clock covers the whole pressure span. IMU and joint_state values outside their own span are edge-held by _resample, and the validity flag it returns is discarded. The build docstring claims validity of uncovered frames is 'carried by hand_pose_valid / cam_<name>_idx = −1', but nothing covers IMU or joint_state: q_valid_mask/qd_valid_mask return all-True for joint-state q. The baseline therefore trains on held (fabricated) q with qd=0, and IMU features before the IMU starts are held values.
- suggested fix: Keep the valid mask from _resample for IMU and joint_state. Store it (e.g. q_valid / imu_valid) and AND it into q_valid_mask/qd_valid_mask and the IMU dataset eligibility, or crop to the reference streams even with span=pressure.

### [LOW] DP-9: Stale-episode detection misses re-applied sync, contrary to its docstring

- files: robot_skin/datasets/build.py, docs/DATA_FORMAT.md
- problem: _source_fingerprint hashes only file names and sizes. Its docstring says it 'changes when ... the sync rewrites stream files', and DATA_FORMAT §4 says re-applied sync is reported as stale. Re-applying clock models (apply_clock_models, the documented way to reuse another session's models, or sync_session(save=False)) rewrites timestamps.npy and the npz 't' in place with identical sizes. build_all then reports the episode as plainly 'skipped' (not stale), and the processed episode keeps the old stream alignment.
- suggested fix: Include a content hash of the time vectors (e.g. sha1 of `t` / timestamps.npy, or of their first/last/sum) or file mtimes in _source_fingerprint. Alternatively, include manifest.calibration['sync'] and have apply_clock_models record the applied models in the manifest.

### [LOW] DP-10: IMU offsets without `imu_sites` are applied to the wrong sites when imu.npz is not in layout order

- files: robot_skin/datasets/build.py, robot_skin/pose/imu_model.py, docs/DATA_FORMAT.md
- problem: DATA_FORMAT says `imu_offsets` are in IMU (file) site order. build first reorders the IMU columns to layout order (`q = q[:, cols]`), then calls imu_calibration_from_dict(man.calibration, sites) with the layout-ordered names. When the calibration dict has no `imu_sites` key, only the length is checked, and file-ordered offsets are applied to layout-ordered sites. Wrong mounting corrections of up to 20° result, with no note. The recorder and synthetic always write imu_sites, but externally produced or legacy calibrations following the table do not have to.
- suggested fix: When imu_sites is absent, interpret offsets in the imu.npz `sites` order: reorder with the file names before selecting `cols`, or pass the file site order to imu_calibration_from_dict and then permute. Alternatively, make imu_sites mandatory and raise without it.

### [LOW] DP-11: Fake acquisition scene: press signal and the geometric self-touch labels preprocessing derives from its hand pose disagree

- files: robot_skin/acquisition/fake.py
- problem: FakeScene claims 'physically consistent raw streams'. But its press model (per-step press on chosen taxels) is independent of the MANO geometry that datasets.build uses for contact_label. On a `glove_logger --fake` D1 session, 93 % of truly pressed taxel samples get label −1 (pinch_index/ring/pinky, palm_touch_thumb/index/middle and finger_crossing are never labelled). Also, 78 of 367 label-1 samples (finger_crossing, middle_tip) have no press at all. The --fake end-to-end path therefore trains and evaluates the contact detector on mostly wrong or missing positives.
- suggested fix: Derive the fake press from the same geometric self-touch (pose.mano.self_touch_from_hand penetration) that preprocessing uses, as datasets.synthetic does. Alternatively, make the fake hand poses actually bring the pressed taxels into contact.


## online

### [HIGH] CTRL-1: A single non-finite joint reading at startup/begin_rollout poisons SafetyFilter.q_last -> NaN position commands sent to the robot on every tick

- files: robot_skin/control/safety.py, robot_skin/control/runner.py
- problem: SafetyFilter.reset(q_current) (safety.py:171-176) only np.clip()s the measurement, which keeps NaN. PolicyRunner.startup() (runner.py:500-502) and begin_rollout() (runner.py:587-594) reset the filter from ONE raw driver read. If that read has a NaN (the docs expect drivers to produce non-finite q: DEPLOYMENT.md §7.1, and online.py holds it in the processor), q_last gets NaN. Every later filter() computes prev + clip(q - prev), which is NaN (safety.py:324-338), and q_last stays NaN forever. The 'non-finite target -> hold last command' rule (safety.py:299-301) only checks q_target and falls back to prev, which is itself NaN. startup() also sends that NaN q_hold directly during the baseline window (runner.py:502,511). Result: send_joint_targets receives NaN for that joint on every tick of the rollout.
- suggested fix: In SafetyFilter.reset, reject non-finite entries: keep the previous q_last for those joints, or raise so the caller retries the read. In filter(), guard prev with np.isfinite and never emit a non-finite command (hold or trigger the e-stop instead). In the runner, re-read state until it is finite before calling reset() in startup() and begin_rollout().

### [HIGH] CTRL-2: Camera watchdog never escalates: camera stamps are only fed on policy ticks, so the stale state is cleared on every other tick

- files: robot_skin/control/runner.py, robot_skin/control/safety.py, robot_skin/stages/deploy.py, docs/DEPLOYMENT.md
- problem: PolicyRunner.step() adds camera stamps to `stamps` only on policy ticks (runner.py:727-731). On the other 9 of 10 ticks, stamps holds only pressure and joint_state. SafetyFilter._watch (safety.py:217-241) treats 'no stale stream in this tick's stamps' as recovered: it emits stale_off and resets _stale_since=None. So a dead or frozen camera toggles stale_on/stale_off every 50 ms. _stale_since restarts at each policy tick, so the documented e-stop (deploy default watchdog camera_*: 0.5 s, estop_after_s: 0.5 s; DEPLOYMENT.md §5 rule 2) never fires. The hold is applied on only 1 tick in 10, so the hand keeps executing policy targets computed from a stale image indefinitely.
- suggested fix: Keep the last-known timestamp of every watched stream in the runner (or in SafetyFilter) and evaluate the full set on every tick. Alternatively, only clear stale state when every previously stale stream has reported a fresh stamp. Add a test with a camera that freezes.

### [MEDIUM] CTRL-3: Real-clock overruns are followed by back-to-back catch-up ticks: the per-tick velocity clamp is exceeded ~10x in wall time, and the tick-based tactile timing (qd, history, FSM) is corrupted

- files: robot_skin/control/runner.py, robot_skin/control/safety.py, robot_skin/control/online.py, robot_skin/control/latency.py, docs/DEPLOYMENT.md
- problem: PolicyRunner._advance (runner.py:466-477) only resynchronises when a tick is more than 10*dt late. For any smaller delay it does not sleep, so the missed ticks run back-to-back. SafetyFilter clamps |dq| <= max_vel*dt per tick using the nominal dt (safety.py:324-329), not the elapsed time. Synchronous inference plus retargeting takes ~12-47 ms on CPU (DEPLOYMENT.md §6 says CPU overruns on every policy tick). Each policy tick is therefore followed by ~8 ticks sent within about 2 ms, each moving max_vel*dt. The commanded speed then far exceeds max_vel, which contradicts latency.py's claim that overruns 'degrade smoothness rather than safety'. The same burst feeds the processor samples that are not 1/hz apart. CausalJointVelocity, TactileHistory strides and SaturationFSM all assume uniform ticks, as in training. The baseline model therefore gets wrong qd (even with the wrong sign), which also corrupts residuals and levels. Levels drive the tactile stop.
- suggested fix: Do not catch up: when a tick starts more than one period late, re-anchor the deadline (skip the missed ticks) instead of bursting. Also make SafetyFilter limit |dq| by max_vel*(t - t_last_command), capped at one period, rather than the nominal dt. Run inference asynchronously, or feed the processor on a uniform grid (for example, hold ticks during inference).

### [HIGH] CTRL-4: Glove-trained hand_mano policies get robot URDF-root-frame taxel poses at deployment (trained on MANO wrist frame): 90-degree-rotated, out-of-distribution tactile positions

- files: robot_skin/control/runner.py, robot_skin/control/online.py, docs/ARCHITECTURE.md, docs/VTLA.md
- problem: VTLA hand_mano bundles are trained on glove episodes whose taxel_pos/nrm are in the MANO wrist frame (preprocessing taxel_frame=mano_wrist: fingers along -x, palm normal -y). On the robot, PolicyRunner._policy_tick passes frame.pos/frame.nrm straight from the processor's robot_pose_fn (runner.py:682). Those poses are in the URDF root frame (synthetic hand: fingers +z, pads +x). No robot-to-human frame change is applied: the retargeter has human_to_robot but the observation does not. The tactile encoder's Fourier/normal pose features therefore see a rotated, shifted pose distribution never seen in training. docs/ARCHITECTURE.md §4/§5.2 and VTLA.md §3.2 claim the hand/robot-base frame lets glove and robot share the encoder. DEPLOYMENT.md §4 lists the remaining train/deploy differences and does not mention this one. This is the default path: the vtla stage defaults to hand_mano on glove D2 data, then deploy runs on the robot.
- suggested fix: Record the training taxel frame (e.g. preprocessing.taxel_frame / kind) in the bundle's tactile section. At deploy, when it differs from the robot's, map the robot poses into the policy's frame, e.g. R_h2r^T (p - p_wrist) with the retarget scale. Otherwise refuse or warn loudly. Also correct the docs that claim frame compatibility.

### [MEDIUM] CTRL-5: With safety.max_acc set, the acceleration clamp overrides the tactile freeze: the command keeps closing past the freeze position by ~v^2/(2a)

- files: robot_skin/control/safety.py, docs/DEPLOYMENT.md
- problem: SafetyFilter.filter applies the tactile stop (freeze closing joints at the measured q, safety.py:311-320) before the rate limits. The acceleration clamp (safety.py:330-335) then refuses to decelerate faster than max_acc, so a joint closing at speed continues past _q_freeze into the object. DEPLOYMENT.md §5 says the first applicable rule wins, with the tactile stop (rule 4) ahead of acceleration (rule 7). The e-stop and watchdog paths return before the clamps; only the tactile freeze is overridden.
- suggested fix: Re-apply the freeze after the rate limits: for frozen closing joints, clip the final q to not exceed q_freeze in the closing direction. Or exempt stop-decelerations from the acceleration clamp and set v_last accordingly.

### [MEDIUM] CTRL-6: Non-finite policy output (or one NaN joint reading on a policy tick) aborts run() with an exception: no robot.stop()/estop, deployment log never written

- files: robot_skin/control/runner.py, robot_skin/action/chunking.py, robot_skin/stages/deploy.py, docs/DEPLOYMENT.md
- problem: DEPLOYMENT.md §5 rule 3 says 'non-finite target -> hold last command (always)', and §7.1 says the processor holds a non-finite q. But _policy_tick builds the robot_joint state/proprio from the raw driver q (runner.py:620-622, 675), and make_absolute adds that state to the chunk. Any NaN in the state or the policy output reaches TemporalEnsembler.add, which raises ValueError('chunk contains non-finite values') (chunking.py:188-189) before SafetyFilter sees anything. run() (runner.py:766-789) and deploy.run have no try/finally. The rollout dies mid-motion, robot.stop()/estop() are never called, and DeploymentLogger.close() never runs. Only events.jsonl, layout.yaml and robot.urdf exist; there is no pressure.npz, joint_state.npz, session.json or deploy_log.npz for the failing run.
- suggested fix: Wrap the rollout loop in try/finally: on any exception, trigger the safety e-stop, send the hold, then call robot.stop() and logger.close(). In _policy_tick, skip non-finite chunks (count an event and keep the previous target). Build the state from the processor's held q (frame.q, mapped back) instead of the raw read.

### [LOW] CTRL-7: Overriding policy_hz silently changes the trajectory time scale: chunk entries stay spaced by the training stride, and the mismatch warning only fires when policy_hz is None

- files: robot_skin/control/runner.py, robot_skin/stages/deploy.py, docs/DEPLOYMENT.md
- problem: chunk[i] is trained as a[t + (offset+i)*stride], with stride = source_hz/bundle.policy_hz. The ensembler and interpolation treat chunk entries as one runner policy period apart (policy_every = round(control_hz/policy_hz), runner.py:346-347).
